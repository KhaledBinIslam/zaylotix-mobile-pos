# Architecture Notes — Zaylotix POS/ERP

Research snapshot, 2026-10-18, gathered via 6 parallel read-only code audits before the Phase 0-9 fix effort. File:line references are accurate as of this commit; re-verify before relying on them in future work since the codebase keeps moving.

## 1. Shop provisioning

- Two production code paths create a `Shop` row: `App\Support\ShopProvisioner::provision()` (`app/Support/ShopProvisioner.php:18-70`, used by self-serve signup, admin "Create Shop", and `DemoShopSeeder`) and a **second, independent** path, `Admin\ShopController::createBranch()` (`app/Http/Controllers/Admin/ShopController.php:176-224`), which hand-rolls its own transaction and never calls `ShopProvisioner`.
- `ShopProvisioner::provision()` is atomic (one `DB::transaction`) but **not idempotent** — a duplicate-phone race throws an uncaught `QueryException`. Only `DemoShopSeeder::provisionOrReuse()` (`database/seeders/DemoShopSeeder.php:79-97`) checks-before-create; the admin/signup paths rely solely on request validation.
- `ShopProvisioner` resolves category/unit/feature defaults from `config('business_types.<slug>')` — a static PHP file — keyed by `BusinessType.slug`, a DB row **independently editable** from Admin → Business Types (`app/Http/Controllers/Admin/BusinessTypeController.php:19-32`). If an admin creates a new `BusinessType` with no matching config entry, provisioning silently creates **zero categories/units/features** for that shop (loop bodies at `ShopProvisioner.php:37-44/46-53` never execute). This is the most likely root cause of "new shop missing defaults."
- `ShopProvisioner::provision()` calls `Tenancy::clear()` before returning (line 65) — every caller must manually `Tenancy::set($shop->id)` again afterward or silently see zero rows on subsequent tenant-scoped reads. Three near-duplicate warning comments in `DemoShopSeeder.php` (lines 133, 229-234, 431) show this has already bitten the codebase once; it should arguably be owned by `ShopProvisioner` itself.
- `BusinessType::hasField()` (`app/Models/BusinessType.php:24-27`) and the `fields` config array are dead code — never read anywhere; actual field visibility is driven by `Feature` flags instead.
- Business type is a one-time suggestion for categories/units/features (freely overridable), with exactly **one** hard lock: `Shop::isRestaurant()` (`app/Models/Shop.php:265-268`) for POS-screen routing, deliberately not feature-flag-driven after a past incident (`Shop.php:245-257`). Features themselves are fully mixable across verticals.
- No roles/permissions table exists; `User::hasPermission()` (`app/Models/User.php:57-64`) always returns true for owners — nothing to provision there. Invoice counter, VAT/loyalty settings all have safe DB-level defaults (`database/migrations/2024_01_01_000002_create_shops_table.php:37-41`, `2026_07_30_000003...:22-23`) and need no provisioning code.

## 2. Variant / pharmacy / unit / cosmetics systems

- **Variants** (`app/Models/ProductVariant.php`, `ProductVariantController.php`) are fully built and additive: grid bulk-entry (`bulkStore`, lines 100-163), pre-existing-stock reconciliation (`reconcilePreExistingStock`, 179-223), POS chip picker (`Pos/Index.vue:1097-1108`), barcode-first resolution, cross-branch exchange with batch/serial cross-branch explicitly blocked (`ReturnController.php:389-393`). `products.stock` is kept as a live sum-of-variants invariant throughout.
- **Pharmacy/FEFO**: `app/Support/BatchStock.php` fully implements FEFO draw/restore/transfer; checkout blocks the sale outright if sellable (non-expired) stock is insufficient (`PosController.php:300-305`) — expired batches cannot be sold. Box→strip→piece conversion exists generically via `Unit`/`ProductUnit` (integer `factor >= 2`, `ProductUnitController.php:22`). Generic-name search, prescription-note-at-checkout, and expiry alerts (`SendExpiryAlerts` command) are all built — **but the alert command's cron registration was not confirmed** in this pass; verify before assuming it fires in production.
- **Decimal qty / multi-unit**: `sold_by_weight` + `decimal:3` casts support fractional stock almost everywhere (checkout, damage, return, stock count, transfer, stock-in, service tickets, purchases). Two genuine gaps: (a) `weight_unit` enum is hard-locked to `kg`/`litre` only (`StoreProductRequest.php:44`, `Stock/Index.vue:671-673`) — no meter/feet/yard support for hardware/textile; (b) `QuotationController.php:53` forces integer qty and excludes variant/pack products by design — blocks fractional-kg quotations.
- **Cosmetics** has no dedicated code — purely a `config/business_types.php` profile reusing `product_variants` (shades) + `batch_tracking` (expiry). No gap.

## 3. Offline sync & stock-page 500

- Offline queue: `resources/js/support/offlineDb.js` (IndexedDB) + `offlineQueue.js` + `composables/useOfflineSync.js`. Checkout POSTs to `app.pos.checkout`; on network failure the payload is queued; on `online` it's replayed sequentially via `trySync()`.
- **Confirmed core fragility — no idempotency key.** `enqueueSale()` generates a `crypto.randomUUID()` but never attaches it to the payload or sends it to the server (`offlineQueue.js:5-13`, `useOfflineSync.js:66`). `CheckoutRequest` has no `client_uuid` field; `PosController::performCheckout()` has zero duplicate-detection. If a queued sale's response is lost after the server already committed (tab closed mid-request, timeout), the entry stays `pending` and gets resubmitted on the next sync — creating a duplicate `Sale` and double-decrementing stock. This is the single highest-value idempotency fix for Phase 1.
- No receipt/print/WhatsApp opportunity right after an offline sale is queued, and no notification when a queued sale finishes syncing — incomplete UX, not a correctness bug. The sync-status banner/failed-items sheet in `AppLayout.vue:407-486` is otherwise solid.
- **Stock-page 500, concrete root cause found**: `ProductController::stockIn()` (`app/Http/Controllers/App/ProductController.php:307-309`) re-fetches the product under `lockForUpdate()` but, unlike its sibling `ProductVariantController::stockIn()`/`::destroy()` (which guard with `if (! $locked) abort(422, ...)`), has **no null-guard** — if the product was soft-deleted between route-binding and the re-fetch, `$locked` is `null` and the strictly-typed `StockIn::apply(Product $lockedProduct, ...)` throws an uncaught `TypeError`. This is the clearest, most fixable concrete defect in this flow. A secondary, narrower edge case: `StockIn.php:22-27` can divide by zero if `stock + qty === 0` (requires pre-existing negative stock).
- A global exception handler already exists (`bootstrap/app.php:46-87`, Laravel 12 style, no `app/Exceptions/Handler.php`) and correctly returns friendly Bengali messages (or JSON for `expectsJson()` callers) for 419/403/404/429/500/503 — so the "500 error" Khaled sees is this friendly screen/JSON body, not a raw stack trace, but the underlying crash above is still real and worth fixing at the source.

## 5. Customer due ledger / returns / void / exchange

- `Customer.due` (`app/Models/Customer.php`) is a **single running total**, no per-invoice link. `Payment` has no `sale_id`. `Sale` has no `due` column. There is genuinely no way today to answer "which specific invoices does this customer still owe on" — only "how much in total, right now." This is a structural gap, not a bug per se, but it's the root cause of the exchange bug below and worth flagging for Phase 3.
- **Returns reducing due — ALREADY CORRECT.** `ReturnController::process()` (lines 460-500) splits the refund proportionally between the due-at-checkout share and the paid share, applies the due portion first (capped at the customer's *current* due), and only pays cash for the remainder. No fix needed.
- **Void/delete reversing due — ALREADY CORRECT, transactional.** `SalesController::destroy()` → `SaleReversal::reverse()` (`app/Support/SaleReversal.php:25-92`) restores stock (product/variant/batch/serial, all locked) and reverses due/cash in one transaction. One latent caveat inherited from the ledger gap above: the reversal recomputes "how much of this sale was due" from the sale's original numbers, not a live per-invoice balance, so if the customer partially paid down that specific sale's due via a later lump payment before the void, the reversal can over/under-correct — a downstream symptom of #1, not a bug unique to void.
- **Exchange math — CONFIRMED REAL BUG.** `ReturnController::createExchangeSale()` (lines 657-816) correctly computes `net_settlement = newTotal - credit` for moving cash/due at the moment of exchange (line 718), but persists the **gross** `newTotal` as the exchange `Sale.total` (line 770) — the trade-in credit is never recorded as a `SalePayment` or any persisted field; `net_settlement` is explicitly a non-DB, response-only property (line 805). Every later read of this sale — `Sales/Show.vue:27-30` (invoice view, printed/WhatsApp memo, and the installment-plan-seeding flow) — recomputes "due" as `total - tendered`, which ignores the trade-in credit and overstates the due/remainder by exactly the credit amount. Worked example confirmed: trade in ৳55, take ৳100 item, pay ৳45 net in cash → customer owes ৳0, but the memo shows "বাকি বিল: ৳55" and a cashier could even spin up a bogus ৳55 installment plan for it.

## 6. Supplier / purchase management

- **New supplier free-text name — CONFIRMED BUG.** The purchase form (`More.vue:689-696`) explicitly invites typing a new supplier name when "not in list," but `PurchaseController::store()` (lines 51-53) just stores the raw string; no lookup-or-create `Supplier` row is ever made, so it never appears in `Suppliers/Index.vue`. Compounding effect: a credit purchase with a free-text-only supplier has **no payable tracked anywhere** (`applyEffects()` only increments payable `if supplier_id` is present, lines 144-150).
- **Can't create a new product from the purchase form — MISSING FEATURE** (not a regression): the product field is dropdown-only (`More.vue:722-729`), validated against existing ids only.
- **"No mark received button" — could not reproduce**: the button, status check, route, and permissions all line up correctly (`Purchases/Index.vue:35`, `PurchaseController.php`, `routes/web.php:313`). If Khaled still can't see it, check the `purchases` feature/permission flag on that shop, or confirm he's looking at the Purchase History page and not the purchase-creation sheet.
- **One-click receive — already correct**: `markReceived()` (lines 95-132) is a single locked transaction reusing the same `applyEffects()` as an immediate purchase — stock, batch (with `supplier_id`), serials, and cost are all updated atomically.
- **Partial supplier return — already works**, with two caveats: variant products are blocked entirely from this flow ("reduce stock from Stock page instead"), and a free-text-only supplier return can't decrement payable (same root cause as the bug above).
- **Per-supplier ledger page — MISSING FEATURE, confirmed from scratch.** No `show()` method, no route, no Vue page. Worse: `SupplierPaymentController::store()` only decrements `Supplier.payable` and cash/bank and writes an `Activity` log line — it **never persists a structured `SupplierPayment` row**, so there is no queryable payment history table to build a ledger page from even once the page exists; that table needs to be created too.

## 8. UI/UX design-token system (Phase 9 research, 2026-10-18)

- **Token inventory**: one global stylesheet, `resources/css/app.css` (764 lines), `:root` block at lines 5-82 — colors (`--bg/--panel/--ink/--mut/--line/--green/--gold/--rose/--sky/--purple/--wa` + `*Soft` variants), a 3-step radius scale (`--radius-sm/md/lg`, 10/14/20px) plus two older radius tokens (`--r`:16px, `--r2`:22px) kept for back-compat, a 7-step spacing scale (`--space-1..7`), one display-font token (`--font-display`), and a single shadow token (`--sh`). No font-size scale, no elevation (multi-shadow) scale.
- **App/* (shop-facing, ~70 files) — token-driven with moderate, fixable drift.** `.card`/`.row`/`.pill`/`.stat`/`.btn`/`.empty` are genuinely shared, widely-reused CSS classes (correctly token-backed). Drift is concrete and narrow: ~15 files hardcode literal `border-radius` px instead of the existing `--radius-sm/md/lg` scale (`AppLayout.vue`, `Stock/Index.vue`, `Pos/Index.vue`, `Home.vue`, `Returns/Index.vue`, `Loans/Index.vue`, `Employees/Payroll.vue`, `CashLedger/Index.vue`, `Activity/Index.vue`, `Clothing/Pos.vue`, `Public/Rate.vue`, `More.vue`); a handful of literal hex values duplicate existing tokens (`Help/Index.vue:28` `#25D366` ≈ `--wa`, `BarcodeLabels/Index.vue:164` `#fff`/`#ddd` ≈ `--panel`/`--line`); `app.css:185`'s `.stat.sky` background (`#E3EFFB`) is a one-digit-off near-duplicate of the actual `--skySoft` token (`#E4EFFB`) defined two lines away in `:root`. `ReceiptMemo.vue`'s raw hex values are intentional (printed receipts must render fixed black/white) and excluded from this.
- **Admin/* (platform backoffice, ~15 pages) — a second, untokenized design system.** `AdminLayout.vue` has zero `var(--...)` usage (vs 9 in `AppLayout.vue`); every Admin page is built from stock Tailwind defaults (`bg-white`, `rounded-xl`, `text-emerald-600`, arbitrary-value hex like `[background:#7C3AED]`) with no relationship to the app.css token set — `#7C3AED` (= the existing `--purple` token, unused outside the Landing page) appears as a raw literal 25+ times across Admin/* alone. `tailwind.config.js` does no `theme.extend.colors` bridging to the CSS custom properties — this is *why* Admin reaches for Tailwind's own palette. Admin also has no shared `.card`/`.btn`/`.pill`-equivalent component; each page hand-rolls its own card/button markup.
- **Dark mode**: does not exist at all — no `prefers-color-scheme`, no `.dark`/`data-theme`, no `dark:` Tailwind usage anywhere. Net-new feature, not a retrofit.
- **Typography**: font-family is genuinely consistent (body = Inter/Hind Siliguri stack set once on `body`; `var(--font-display)` deliberately applied to exactly 12 heading-level selectors, zero stragglers). Font-*size* has no token scale — 39 distinct literal px values inline across templates plus ~29 more inside app.css's own selectors; a de facto convergence around 12/12.5/13/14-16px exists by copy-paste convention only, not an enforced scale.
- **Shared components, genuinely reused**: `Sheet.vue` (the real modal/bottom-sheet primitive, backed by `#sheet`/`#scrim` CSS), `Toast.vue`, `Pagination.vue`, `HowToHint.vue`, `ReceiptMemo.vue`, `ZaylotixLogo.vue`/`Mark.vue`. **Confirmed dead code**: the original Breeze scaffold components (`PrimaryButton.vue`, `SecondaryButton.vue`, `TextInput.vue`, `InputLabel.vue`, `InputError.vue`, `DangerButton.vue`, `Checkbox.vue`, `Modal.vue`) have zero imports anywhere in `resources/js` — actual inputs/buttons are styled via app.css's global element selectors instead. Safe to delete, but that's a file-deletion action, not a token change — flagged, not done, in Phase 9.
- **Accessibility (passing notes only)**: `--dim` (`#93A99A`) on white is ~2.9:1 contrast, below AA's 4.5:1, used pervasively for secondary/quiet text. A few small controls (`.qbtn`, `.sheet-close` 30×30px, `.scan-x` 40×40px) sit under a comfortable ~44px tap target, despite `.btn` itself having already had a deliberate 44px+ pass (app.css:207-213).
- **Performance**: not a bundle-size concern (only 6/75 page files have any `<style>` block, all small). 1,439 inline `style="..."` attributes exist across Pages/Layouts — a maintainability tax (can't be changed via a single token edit), not a current perf problem. `.pcard`'s `content-visibility:auto` (app.css:372) shows the team already handles this class of problem where it matters.
- **Scope decisions flagged for Khaled, not assumed** (see Phase 9 in FIX_PLAN.md for the safe-default work done instead): (1) add dark mode at all — net-new, no existing infra; (2) unify Admin's purple identity with App's green/gold brand, or keep Admin deliberately distinct as an "internal console" look; (3) the PWA install theme color (`app.blade.php`, `manifest.json`) currently matches Admin's purple, not the in-app functional palette — may be intentional outward-brand-identity, may be an oversight; (4) bump `--dim`'s contrast — a one-line token edit, but a visible app-wide color shift on every "quiet" text element; (5) add a loading-skeleton state — none exists anywhere today, and doing it right needs a template conditional per page, not just CSS; (6) delete the 8 confirmed-unused Breeze components.
